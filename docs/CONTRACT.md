# BabyTracker — технический контракт

Единый источник правды для всех модулей. Менять только через согласование: на этот файл
опираются server, dashboard и tv одновременно.

## 0. Глоссарий

- **utterance** — сырая фраза, как её распознала Алиса. Хранится всегда, даже если разбор упал.
- **event** — распознанное событие жизни ребёнка. Может быть *открытым* (`ended_at IS NULL`) —
  например, начавшийся и ещё не закончившийся сон.
- **fast-path** — детерминированный матчер, отвечает Алисе за <50 мс.
- **worker** — фоновый процесс, гоняет `claude -p` по очереди utterances.

## 1. Схема БД (SQLite, WAL)

Файл: `data/babytracker.db`. Все временные метки — **ISO 8601 в UTC** (`2026-09-15T14:32:05.123Z`).
Никаких локальных времён в БД; таймзона применяется только на слое представления.

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS events (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  child_id     TEXT    NOT NULL DEFAULT 'andrey',
  type         TEXT    NOT NULL,   -- 'sleep' | 'feed' | 'diaper' | 'measure' | 'meds' | 'note'
  subtype      TEXT,               -- см. §2
  started_at   TEXT    NOT NULL,   -- ISO8601 UTC
  ended_at     TEXT,               -- NULL = событие ещё идёт
  value_num    REAL,               -- мл / г / °C / см
  value_unit   TEXT,               -- 'ml' | 'g' | 'kg' | 'c' | 'cm' | 'min'
  note         TEXT,
  source       TEXT    NOT NULL,   -- 'alice-fast' | 'alice-llm' | 'api' | 'manual'
  utterance_id INTEGER REFERENCES utterances(id),
  confidence   REAL,               -- 0..1, чем распознал fast-path/LLM
  created_at   TEXT    NOT NULL,
  updated_at   TEXT    NOT NULL,
  deleted_at   TEXT                -- мягкое удаление; все выборки фильтруют IS NULL
);

CREATE INDEX IF NOT EXISTS idx_events_started ON events(started_at DESC);
CREATE INDEX IF NOT EXISTS idx_events_type    ON events(type, started_at DESC);
-- ключевой индекс: поиск открытого события (незакрытый сон)
CREATE INDEX IF NOT EXISTS idx_events_open    ON events(type, ended_at) WHERE ended_at IS NULL;

CREATE TABLE IF NOT EXISTS utterances (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  raw_text      TEXT    NOT NULL,
  alice_user_id TEXT,
  session_id    TEXT,
  received_at   TEXT    NOT NULL,
  status        TEXT    NOT NULL DEFAULT 'pending', -- pending|processing|done|failed|skipped
  fast_result   TEXT,    -- JSON: что понял fast-path
  llm_result    TEXT,    -- JSON: что вернул claude
  llm_error     TEXT,
  attempts      INTEGER NOT NULL DEFAULT 0,
  processed_at  TEXT
);

CREATE INDEX IF NOT EXISTS idx_utt_status ON utterances(status, received_at);
```

**Правило открытого сна:** в каждый момент времени может существовать не более одного
события `type='sleep' AND ended_at IS NULL AND deleted_at IS NULL`. Перед вставкой нового
открытого сна — закрыть предыдущий (или отклонить). Это инвариант, проверяется в коде.

## 2. Словарь типов

| type      | subtype                          | value_num / unit         |
|-----------|----------------------------------|--------------------------|
| `sleep`   | `night` \| `nap`                 | —                        |
| `feed`    | `breast` \| `bottle` \| `solid`  | объём `ml` / длит. `min` |
| `diaper`  | `wet` \| `dirty` \| `both`       | —                        |
| `measure` | `weight` \| `height` \| `temp`   | `g`/`kg`, `cm`, `c`      |
| `meds`    | свободный текст препарата        | доза `ml` / `mg`         |
| `note`    | —                                | —                        |

**В MVP реально распознаётся только `sleep`.** Остальные типы уже есть в схеме и в MCP-тулах,
чтобы расширение не требовало миграций — но словарь fast-path и промпт LLM в MVP заточены на сон.

## 3. HTTP API

Базовый порт: **8787** (3000 слишком часто занят чем-то другим).

### 3.1 `POST /alice/:secret` — webhook Яндекс Диалогов

Секрет — 32 hex-символа из `ALICE_WEBHOOK_SECRET`. Сравнение **constant-time**.

Проверки, по порядку (любая неудача → 200 OK с нейтральным текстом, не 4xx: Алиса не должна
показывать пользователю ошибку, а атакующий — различать причины отказа):
1. секрет в пути совпадает;
2. `session.skill_id === ALICE_SKILL_ID` (если переменная задана);
3. `session.user_id` входит в `ALICE_ALLOWED_USER_IDS` (если список задан; пустой = принимать всех,
   это режим первичной настройки — в логи пишется увиденный `user_id`, чтобы его прописать).

Вход (существенная часть, полная схема — https://yandex.ru/dev/dialogs/alice/doc/ru/request):
```jsonc
{
  "meta":    { "locale": "ru-RU", "timezone": "Europe/Moscow", "interfaces": {} },
  "session": { "message_id": 0, "session_id": "...", "skill_id": "...",
               "user_id": "...", "new": true },
  "request": { "type": "SimpleUtterance", "command": "андрей заснул",
               "original_utterance": "Андрей заснул",
               "nlu": { "tokens": [], "entities": [], "intents": {} } },
  "version": "1.0"
}
```

Выход:
```jsonc
{ "response": { "text": "Записала: Андрей заснул в 17:32", "tts": "...", "end_session": false },
  "version": "1.0" }
```

Поведение:
- `session.new === true` и пустой `command` → приветствие, `end_session: false` (сессия держится
  открытой, чтобы можно было надиктовать несколько событий подряд).
- Команды выхода (`хватит`, `стоп`, `выход`, `пока`, `отмена`) → прощание, `end_session: true`.
- Иначе: записать utterance → прогнать fast-path → ответить. **Бюджет — 200 мс.**
  Запись в очередь и SSE-рассылка не должны блокировать ответ.
- `text` и `tts` — максимум 1024 символа каждое.

### 3.2 `GET /api/state` — текущее состояние для дашборда

```jsonc
{
  "now": "2026-09-15T14:32:05.123Z",
  "child": { "name": "Андрей", "birthDate": "2026-03-01", "ageDays": 198 },
  "sleep": {
    "status": "asleep",                      // "asleep" | "awake"
    "since": "2026-09-15T13:10:00.000Z",     // начало текущего состояния
    "currentDurationMin": 82,
    "lastSleep": { "startedAt": "...", "endedAt": "...", "durationMin": 95 }
  },
  "today": {
    "date": "2026-09-15",                    // локальная дата в TZ сервера
    "sleepTotalMin": 430,
    "sleepSessions": 4,
    "longestSleepMin": 180
  },
  "pending": 0                               // сколько фраз ещё разбирает worker
}
```

### 3.3 `GET /api/events`

Query: `from` (ISO), `to` (ISO), `type`, `limit` (по умолчанию 200, максимум 1000).
Ответ: `{ "events": Event[] }`, отсортировано по `started_at DESC`.

### 3.4 `GET /api/sleep/daily?days=14`

```jsonc
{ "days": [ { "date": "2026-09-15", "totalMin": 430, "sessions": 4, "nightMin": 300, "napMin": 130 } ] }
```

### 3.5 `GET /api/utterances?limit=20`

Лента последних фраз со статусом разбора — нужна дашборду для «живого» блока распознавания.

### 3.6 `GET /api/stream` — SSE

`Content-Type: text/event-stream`, heartbeat-комментарий каждые 15 с (иначе Cloudflare Tunnel
рвёт соединение). Именованные события:

| event       | data                                              |
|-------------|---------------------------------------------------|
| `state`     | тот же объект, что `/api/state`                   |
| `event`     | `{ "action": "created"\|"updated"\|"deleted", "event": Event }` |
| `utterance` | `{ "id", "raw_text", "status", "fast_result", "llm_result" }`   |

Клиент переподключается сам (EventSource это умеет); сервер обязан пережить обрыв.

### 3.7 `POST /api/events` — ручная запись (отладка, веб-кнопки)

Тело — `Event` без `id`/`created_at`/`updated_at`. `source` принудительно `'manual'`.

### 3.8 `GET /healthz`

`{ "ok": true, "db": true, "worker": { "alive": true, "lastRunAt": "...", "queueDepth": 0 } }`

Сверх контракта воркер отдаёт там же: `oldestPendingAt` (когда пришла самая старая
ждущая фраза) и `queueLagSec`, `claudeAvailable` / `claudeProblem`,
`rateLimited` / `rateLimitedUntil` / `rateLimitReason`. Глубина очереди без её возраста
обманчива: «3 фразы» — норма, «3 фразы, старшей четыре часа» — авария.

## 4. Fast-path матчер (MVP: только сон)

Чистая функция, без побочных эффектов, полностью покрыта юнит-тестами:

```ts
type FastResult =
  | { kind: 'sleep_start'; confidence: number; at?: string }
  | { kind: 'sleep_end';   confidence: number; at?: string }
  | { kind: 'query_state'; confidence: number }
  | { kind: 'exit' }
  | { kind: 'unknown' };

function matchFast(command: string, nlu: AliceNlu): FastResult
```

Нормализация: нижний регистр, `ё`→`е`, схлопывание пробелов, срезание пунктуации.

- `sleep_start`: заснул, уснул, спит, засыпает, уложили, уложил, положили спать, спать пошёл,
  спатки, отрубился, вырубился, задрых
- `sleep_end`: проснулся, просыпается, встал, разбудили, не спит, глаза открыл, пробудился
- `query_state`: сколько спал, как спал, сколько проспал, что там, статус, как дела, отчёт,
  сколько сегодня
- `exit`: хватит, стоп, выход, пока, отмена, закончили

Отрицания (`не заснул`, `ещё не проснулся`) → `unknown`, отдаём на разбор LLM.
Если `nlu.entities` содержит `YANDEX.DATETIME` — превратить в абсолютное время и положить в `at`
(«заснул полчаса назад», «проснулся в три»).

**Ответы Алисы** (короткие, без «ваш», с локальным временем в TZ сервера):
- sleep_start → `Записала: Андрей заснул в 17:32`
- sleep_start при уже открытом сне → `Андрей уже спит, с 17:32. Это 45 минут`
- sleep_end → `Андрей проснулся. Спал 1 час 35 минут`
- sleep_end без открытого сна → `А он и не спал. Записала, что проснулся`
- query_state → сводка из `/api/state` словами
- unknown → `Приняла: «<фраза>». Сейчас разберу` — и LLM доразбирает асинхронно

## 5. Worker + Claude CLI

Цикл: раз в 1 с забрать `utterances` со `status='pending'` (по одной, `attempts < 3`),
перевести в `processing`, запустить:

```
claude -p "<prompt>" \
  --output-format json \
  --model claude-sonnet-5 \
  --mcp-config <path>/mcp.json \
  --allowedTools "mcp__babytracker__log_event,mcp__babytracker__update_event,mcp__babytracker__query_events,mcp__babytracker__get_state,mcp__babytracker__delete_event" \
  --permission-mode acceptEdits
```

Таймаут процесса — **180 с**, после чего kill и попытка сгорает. Ошибки не роняют сервер.
Конкурентность — 1 (не плодим процессы). **Сервер обязан работать без `claude`** (fast-path
продолжает писать сон): LLM — усилитель, не единая точка отказа.

### Недоступность CLI не съедает фразы

«Работает без claude» означает «не падает и отвечает голосом», а **не** «выбрасывает фразы,
пока его нет». С политикой `all` (§9.4) модель зовут на каждую фразу, поэтому единственная
защита дневника — очередь:

- пока `claude` недоступен (не установлен, снесён, протух токен, кончился баланс), воркер
  **очередь не трогает вообще** — так же, как при исчерпанном окне лимита. Фразы остаются
  `pending`, копятся и разбираются по порядку (`received_at ASC, id ASC`), когда CLI вернётся.
  Терминального `skipped` по причине «нет claude» больше не существует;
- доступность проверяется `claude --version` (локальный процесс, вызовом модели не является)
  раз в 5 минут. Проба не проверяет авторизацию, поэтому в случае «`--version` отвечает,
  а разбор падает 401» пауза удваивается после каждого ложного «ожил»: 5 мин → 10 → … → час,
  и сбрасывается первым успешным разбором;
- фраза, на которой обнаружилась недоступность, теряет **одну** попытку. Это осознанно:
  счётчик попыток живёт в базе и переживает рестарт, поэтому даже патология конечна — через
  `MAX_ATTEMPTS` голова очереди становится `failed`, статус, видимый человеку, а не тихий
  `skipped`. Ждущая очередь при этом не стоит ни одного вызова модели;
- терминальный `failed` после трёх настоящих ошибок разбора остаётся терминальным: автоматика
  к такой фразе не возвращается никогда. Вернуть её в работу может только человек —
  `POST /api/utterances/:id/reparse` или пачкой `POST /api/utterances/reparse`
  (`{ ids | statuses: ['failed'|'skipped'], since?, limit? }`, отбор обязателен, потолок 500).

Промпт даёт модели: **момент, когда фраза была сказана** (`received_at`), текущее локальное
время, TZ, состояние ребёнка, сырую фразу и результат fast-path. Точка отсчёта для всего
относительного во фразе («полчаса назад», «в три») — момент фразы, а не момент разбора; иначе
разгребание накопившейся очереди само становится источником неверных времён. Если разбор
запоздал больше чем на 2 минуты, модели об этом сказано прямо. Задача — привести данные
в порядок через MCP-тулы: дописать то, что fast-path не понял, исправить то, что понял
неверно, ничего не дублировать.

# §9. Широкий доступ модели к данным и гарантия обратимости

Заказчик хочет управлять данными голосом свободно: «убери предыдущую запись», «удали всё за
сегодня», «исправь, он заснул в девять, а не в десять». Набор узких тулов под каждый такой
случай не спроектировать — их бесконечно много. Поэтому модель получает **широкий доступ**,
а безопасность обеспечивается не доверием к модели, а конструкцией хранилища.

**Единственное жёсткое требование: безвозвратной модификации данных существовать не должно.**

## 9.1 Три рубежа обороны

Важно, что они независимы: даже если модель обойдёт первые два, третий держит.

1. **Запрет на уровне SQLite.** Триггер `BEFORE DELETE ON events` делает `RAISE(ABORT)`.
   Физически удалить событие нельзя ничем — ни тулом, ни произвольным SQL, ни багом в коде.
   Удаление выражается только через `deleted_at`.
2. **Журнал ревизий.** Каждое изменение пишет снимок строки «до» в append-only таблицу.
   Любую правку можно отменить, даже спустя месяцы.
3. **Снимок базы перед каждым запуском модели.** `VACUUM INTO` в `data/snapshots/`, хранятся
   последние 50. Страховка на случай, если модель наворотит что-то массовое.

## 9.2 Схема

```sql
CREATE TABLE IF NOT EXISTS change_sets (
  id           TEXT PRIMARY KEY,        -- uuid, один на запуск воркера
  utterance_id INTEGER REFERENCES utterances(id),
  summary      TEXT,                    -- что модель сделала, своими словами
  created_at   TEXT NOT NULL,
  reverted_at  TEXT                     -- заполнен, если набор изменений отменён
);

CREATE TABLE IF NOT EXISTS event_revisions (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  change_set_id TEXT NOT NULL REFERENCES change_sets(id),
  event_id      INTEGER NOT NULL,
  op            TEXT NOT NULL,          -- 'insert' | 'update' | 'soft_delete' | 'revert'
  before_json   TEXT,                   -- полная строка events до изменения; NULL для insert
  after_json    TEXT,                   -- полная строка после
  actor         TEXT NOT NULL,          -- 'alice-llm' | 'api' | 'manual'
  created_at    TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_rev_cs    ON event_revisions(change_set_id);
CREATE INDEX IF NOT EXISTS idx_rev_event ON event_revisions(event_id, id DESC);

-- Рубеж 1: физическое удаление невозможно
CREATE TRIGGER IF NOT EXISTS events_no_hard_delete
BEFORE DELETE ON events BEGIN
  SELECT RAISE(ABORT, 'физическое удаление events запрещено: используй deleted_at');
END;

-- Рубеж 2: журнал только дописывается
CREATE TRIGGER IF NOT EXISTS revisions_no_update
BEFORE UPDATE ON event_revisions BEGIN
  SELECT RAISE(ABORT, 'event_revisions доступен только для добавления');
END;
CREATE TRIGGER IF NOT EXISTS revisions_no_delete
BEFORE DELETE ON event_revisions BEGIN
  SELECT RAISE(ABORT, 'event_revisions доступен только для добавления');
END;
```

## 9.3 MCP-тулы: широкая ручка

Прежние высокоуровневые тулы остаются — по ним модели проще и дешевле делать обычные вещи.
Добавляются два широких и два для отмены:

| tool | назначение |
|------|-----------|
| `sql_query`         | **Произвольный SELECT.** Читать можно что угодно и как угодно: любые таблицы, джойны, агрегаты. Один statement, максимум 500 строк. |
| `sql_execute`       | **Произвольные INSERT / UPDATE по таблице `events`.** Один statement. Выполняется в транзакции, все затронутые строки журналируются. |
| `list_change_sets`  | последние наборы изменений с описанием и временем |
| `revert_change_set` | отменить набор изменений по id, восстановив строки из журнала |

### Рамки `sql_execute` — намеренно минимальные

Разрешено: `INSERT INTO events ...`, `UPDATE events SET ...` с любым `WHERE`.

Отклоняется с понятным текстом ошибки (чтобы модель исправилась сама, а не зациклилась):

- `DELETE` — подсказать: «используй `UPDATE events SET deleted_at = ...`»;
- любая таблица кроме `events`;
- `DROP`, `ALTER`, `CREATE`, `TRUNCATE`, `VACUUM`, `ATTACH`, `DETACH`, `PRAGMA`, `REPLACE INTO`,
  `INSERT OR REPLACE`;
- более одного statement (всё после первого `;` вне строкового литерала);
- попытка выставить `id`, `created_at` или перезаписать `utterance_id` чужой записи.

Проверка обязана работать по **токенам, а не по подстрокам**: ключевое слово внутри строкового
литерала (`note = 'не надо delete'`) не должно приводить к отказу, а комментарий `/* */` или
`--` не должен прятать вторую команду. Это место — прямая мишень для обхода, покрой его тестами.

### Отмена голосом

«Отмени последнее», «верни как было» → модель зовёт `list_change_sets`, затем
`revert_change_set`. Сам откат тоже пишется в журнал (`op='revert'`), поэтому **отмену отмены**
тоже можно отменить.

## 9.4 Политика запуска модели

Модель — `claude-opus-5` (env `CLAUDE_MODEL`). Сильная модель здесь оправдана: она пишет SQL по
свободной русской фразе и правит чужие данные, цена ошибки выше цены токенов.

Воркер стартует **немедленно при постановке в очередь**, а не по таймеру: фраза попала в
`utterances` → сразу сигнал воркеру. Опрос раз в секунду остаётся только подстраховкой на
случай потерянного сигнала.

Вызовы идут **через подписку Claude (OAuth), а не по API-ключу** — отдельной оплаты за вызов
нет. Значит ограничитель не деньги, а **скользящие окна лимитов подписки**, и воркер обязан
отличать «лимит исчерпан» от настоящей ошибки: в этом случае фраза остаётся в очереди и ждёт
открытия окна, а не сгорает на трёх попытках.

Экономить вызовы на «уверенно распознанных» фразах оказалось дороже, чем платить за них.
Матчер — словарь: он не видит ни состояния, ни истории, и его 0.95 означает лишь «нашёл
знакомое слово». На проде это трижды приводило к тихой потере факта, причём каждый раз
уверенность была высокой: «покушал и уснул», «заснул полтора часа назад», «закончил кушать
когда лег спать» — последняя ушла в `skipped` как уверенный `sleep_start`, и окончание
кормления не записал никто. Поэтому уверенность матчера больше не повод не звать модель.
Политика в env `LLM_QUEUE_POLICY`:

| значение | когда зовём модель |
|----------|--------------------|
| `all` (**по умолчанию**) | на каждую фразу. Запись матчера уходит модели как черновик (§9.5), и она отвечает за связность журнала целиком |
| `smart`  | fast-path вернул `unknown` или `confidence < LLM_CONFIDENCE_THRESHOLD` (0.8), **либо** фраза похожа на команду управления данными: содержит «удали», «убери», «отмени», «исправь», «поправь», «не так», «ошиблась», «верни», «сотри», «замени» |
| `unknown`| только когда fast-path совсем не понял — самый экономный режим |

Список командных слов держать в одном месте рядом со словарём fast-path.

## 9.5 Что видит модель в промпте

Дополнительно к §5: схема таблиц `events` / `change_sets` / `event_revisions`, правила и рамки
`sql_execute`, последние 5 наборов изменений (чтобы «отмени последнее» имело смысл) и последние
20 событий. Явно сказать: физическое удаление невозможно by design, для удаления — `deleted_at`;
всякая правка обратима, поэтому действовать можно уверенно, но массовые изменения —
только если пользователь попросил именно этого.

## 9.6 API

- `GET  /api/change-sets?limit=20` — история изменений
- `POST /api/change-sets/:id/revert` — откат из веба, той же дорогой, что и у модели
- `GET  /api/events?include_deleted=true` — показать мягко удалённое (для разбора «а что пропало»)
- `POST /api/utterances/:id/reparse` — вернуть в разбор одну фразу
- `POST /api/utterances/reparse` — вернуть пачкой: `{ ids?, statuses?: ['failed','skipped'],
  since?, limit? }`. Только действие человека и только с явным отбором: пустое тело — 400,
  а не «верни всё». Потолок за раз — 500 фраз, по умолчанию 50. `done` в массовый отбор
  не допускается: переписывать уже разобранное можно только по одной фразе

# §10. Полная таксономия событий, несколько событий во фразе, админ-дашборд

## 10.1 Что вообще считают у младенца

Ориентиры из рекомендаций AAP — по ним строятся подсказки на дашборде:

| Показатель | Норма | Почему важно |
|---|---|---|
| Мокрые подгузники | день 1 → 1, день 2 → 2, … с 5-го дня **6+ в сутки** | главный признак достаточного питья |
| Грязные подгузники | **3–4 в сутки** после первых дней | усвоение питания |
| Кормления | **8–12 раз за 24 часа** у новорождённого | достаточность питания |
| Рост | вес, рост, **окружность головы** | перцентили по кривым ВОЗ |

## 10.2 Таксономия

**Объём — необязателен везде.** При смешанном вскармливании граммы имеют смысл только для
бутылочки; грудь измеряют стороной и длительностью. Модель не должна выдумывать числа,
которых мама не называла: отсутствующее значение — это `NULL`, а не ноль.

| type | subtype | value_num / unit | заметки |
|---|---|---|---|
| `sleep` | `night`, `nap` | — | открытое событие до пробуждения |
| `feed` | `breast`, `bottle`, `solid` | `ml` (бутылочка), `min` (грудь) | грудь: сторона в `note` — `left`/`right`/`both` |
| `pump` | — | `ml` | сцеживание |
| `diaper` | `wet`, `dirty`, `both` | — | считаем количество за сутки |
| `measure` | `weight`, `height`, `head`, `temp` | `g`/`kg`, `cm`, `cm`, `c` | окружность головы — `head`; **все названные градусы — сюда**, см. ниже |
| `meds` | название препарата | `ml`/`mg` | витамин D и прочее |
| `symptom` | `spit_up`, `vomit`, `rash`, `colic`, `crying`, `fever`, `skin_yellow`, `eyes_yellow` | `c` (температура) | `fever` — жар БЕЗ числа; `rash` и `*_yellow` — наблюдения-состояния, см. ниже |
| `activity` | `bath`, `walk`, `tummy_time` | `min` | |
| `note` | — | — | всё, что не разложилось |

Неизвестный `subtype` — не повод терять событие: пишем `type` с `note` и живём дальше.

**Список подтипов — один на репозиторий: `shared/taxonomy.ts`.** Он лежал в трёх копиях сразу
(валидация сервера, подписи админки, подписи телевизора), копии были независимы, и ценой
расхождению был не беспорядок, а событие, которое сервер пишет, а экран молча перестаёт
показывать: нет подписи — нет строки, и ошибки при этом тоже нет. Теперь список один, а
обязанность иметь подпись на каждый подтип выражена типом (`SubtypeOf<T>` в ключах таблиц
подписей): забыли подпись — падает `pnpm typecheck`, то есть и CI, где у всех трёх
приложений проверяются типы. Общий файл держит только состав списка; подписи, иконки,
тона, единицы и подсказки промпту остаются у каждого приложения своими.

### Наблюдения-состояния

Большинство симптомов — точки: срыгнул, вырвало, заплакал. Но **сыпь**, **желтизна кожи**
и **желтизна белков глаз** держатся сутками, и врача интересует ровно их протяжённость:
с какого дня появилась и прошла ли. Точками этого не записать — из рассыпанного по ленте
пунктира «с 5-го по 9-й день» уже не собрать: между двумя упоминаниями не отличить
«держалось» от «прошло и вернулось».

Поэтому у `rash`, `skin_yellow` и `eyes_yellow` механика сна: `started_at` — когда заметили,
`ended_at = NULL` — держится до сих пор, `ended_at` — когда сошло. Открытыми они висят
сутками, и это норма: предела правдоподобия (`MAX_OPEN_MIN`) у них нет, «чинить»
провисевшее состояние нельзя. Список пар — `STATE_SUBTYPES` в `shared/taxonomy.ts`,
разрешение на «идёт» выдаётся парой (тип, подтип) через `isDurative`, а не одним типом:
целиком durative `symptom` означал бы, что открытыми могут висеть колики и плач.

**Список закрыт намеренно.** Каждый длящийся подтип — это запись, которую кто-то должен
закрыть словами, а забывают закрывать всё. Состояниями сознательно НЕ стали: `spit_up`
и `vomit` (точки, врач считает частоту), `colic` и `crying` (закрывающей фразы не
существует — «колики прошли» не говорят так, как говорят «сыпь прошла»), `fever` (жар
меряют числом, а числа живут в `measure/temp`, см. ниже).

**Это НАБЛЮДЕНИЕ, а не диагноз, и граница здесь жёсткая.** Родитель видит не болезнь,
а цвет и сыпь. Слова «желтуха» в дневнике нет нигде: ни в подтипе (`skin_yellow`, а не
`jaundice`), ни в подписи интерфейса, ни в `note`, ни в ответе Алисы; ровно так же нет
ни «аллергии», ни «потницы», ни «диатеза» (`rash`, а не `allergy`). Модели это запрещено
прямым текстом в промпте — вместе с причиной, оценкой и советом обратиться к врачу.
Что означает увиденное — решает врач; приложение, записавшее вывод вместо факта,
начинает лечить вместо него.

Кожа и белки глаз разведены **намеренно**: для врача это разные наблюдения. Уточнение
в `note` не годится — это свободный текст, по нему сводку не построить. Тот же принцип,
что у мокрого и грязного подгузника: одно событие, но два признака, и смотрят на них
по отдельности.

Быстрый матчер наблюдения **не разбирает и событий по ним не создаёт** — он отвечает голосом
за секунды и словарём тут не обойтись. Корни `желт`/`жёлт` и `сып` стоят в `DOMAIN_STEMS`
ровно затем, чтобы фраза гарантированно ушла модели (§10.3): «покормила, и он какой-то
желтенький» иначе закрылось бы кормлением, а наблюдение пропало бы молча. Голосовой
ответ — обычное «Приняла».

Разбор поднимается одной ситуативной карточкой на все состояния сразу: правила у них
буквально общие (открыть, не заводить второе поверх открытого, закрыть только явным
словом родителя), различается лишь строка «куда писать». Слово «покраснел» состоянием
НЕ считается: у младенца краснеют от натуги, от жары и перед плачем — это описание
минуты, а не наблюдение о коже.

### Где лежит температура

Градусы разрешены и `measure/temp`, и `symptom/fever` — единица `c` есть у обоих типов.
Из-за этого `dailyStats.tempMaxC` читала только первое место, и **жар, записанный
симптомом, до врача не доезжал вовсе**.

Договорённость: **названные градусы пишутся в `measure/temp`**, а `symptom/fever`
остаётся жаром без числа («горячий», «температурит»). Модели это сказано в подсказке
таксономии.

Но **читать надо оба места, и всегда** — `isTemperatureReading` в `shared/taxonomy.ts`.
Одной договорённости мало по двум причинам: в базе уже лежат записи обоих видов, а
физического удаления в `events` нет (§9) — переписывать настоящие данные ради
единообразия нельзя, запись была верна, неверен был запрос; и исполняет договорённость
модель, а она не детерминирована. Единица принимается `c` или пустая: число без единицы
у температуры — это градусы.

В «Сводке» температура показана фактами: суточный максимум (врачу нужен пик, а не
последний замер), сколько раз мерили, когда был самый высокий. Ни порога, ни ярлыка,
ни цвета — как и на всей странице.

## 10.3 Несколько событий в одной фразе

Мама говорит свободно: «Андрей покушал и уснул», «поменяли подгузник, покакал, и он опять
заснул», «проснулся, поели грудью минут пятнадцать». **Одна фраза — сколько угодно событий.**

### Обязательное исправление fast-path

Сейчас есть прямой путь к потере данных: fast-path распознаёт «покушал и уснул» как уверенный
`sleep_start` с confidence 0.95, политика `smart` видит высокую уверенность и **не отправляет
фразу модели** — кормление исчезает молча, без следа в интерфейсе.

Правило: **fast-path отвечает голосом, но никогда не решает за модель, если во фразе может быть
что-то ещё.** Конкретно, `matchFast` дополнительно возвращает `mayContainMore: boolean`, и он
`true`, если выполнено хотя бы одно:

- во фразе есть союз или перечисление: ` и `, ` а `, ` потом`, ` затем`, ` после`, `,`, ` плюс`;
- встречается ключевое слово из домена, отличного от распознанного (еда, подгузник, измерение,
  лекарство, симптом) — словари те же, что у модели;
- во фразе больше одного числа;
- длина фразы больше 6 значимых слов.

Если `mayContainMore === true`, фраза уходит модели **независимо от confidence и политики**.
Голосовой ответ при этом остаётся мгновенным и по тому, что понял fast-path. Это ровно тот
случай, ради которого политика `smart` вообще имеет исключения.

### Неразрешённое время — второй признак того же класса

Найдено на проде. Фраза «андрей заснул полтора часа назад» при пустом `nlu.entities`:
fast-path распознал `sleep_start` с confidence 0.95, но применить время не смог (`at` пуст)
и записал сон на **текущий момент**. По высокой уверенности фраза не пошла модели, и родитель
увидел правдоподобное, но неверное время — без единого признака ошибки в интерфейсе и в логе.

Мама редко записывает событие ровно тогда, когда оно случилось: «заснул полчаса назад»,
«проснулся в три», «уснул после обеда» — обычный способ говорить. Полагаться на то, что
Яндекс всегда выделит `YANDEX.DATETIME`, нельзя: достаточно формулировки, на которой NLU
не справится, и время уедет молча.

Правило: **если во фразе есть указание на время, а fast-path его не разрешил, он не вправе
заявлять высокую уверенность.** `matchFast` возвращает ещё и `timeUnresolved: boolean`:

```ts
timeUnresolved === hasTimeReference(фраза) && at === undefined
```

Признаки указания на время: `назад`, `в <число>` (`в три`, `в 15`), `утром`, `днём`,
`вечером`, `ночью`, `только что`, `недавно`, `вчера`, `перед`, `после`, `в обед`, `к обеду`,
`под утро`, названия приёмов пищи, `полчаса`, `полтора`, а также слова `минут` / `час` /
`часа` / `часов` и числительные словами рядом с ними. Список заведомо неполный и пополняется
по логам — ошибаться он должен в сторону лишнего вызова модели, а не пропуска.

Пустой `nlu.entities` при наличии слов времени — частный случай того же правила: NLU
не справился, значит решает модель.

При `timeUnresolved === true`:

- confidence опускается до **0.4** (тип события матчер знает, момент — нет), и это значение
  сохраняется в `events.confidence`, чтобы неуверенность была видна в дашборде;
- фраза уходит модели **независимо от confidence и политики**, как и при `mayContainMore`;
- событие всё равно создаётся на момент фразы — при недоступной модели неточная запись лучше,
  чем никакой, — но **голосовой ответ не называет время**: «Записала: Андрей заснул.
  Время уточню» вместо «заснул в 17:32». Озвученное неверное время и есть главный вред;
- модель получает в промпте явное указание поправить `started_at` существующего события,
  а не создавать второе.

**Разбирать относительное время самостоятельно, из текста, сервер не должен.** Русские
временные выражения («без двадцати пять», «в половине четвёртого», «под утро») слишком
разнообразны, а наполовину работающий разбор даёт ровно ту же правдоподобную неправду,
которую это правило и устраняет, — только увереннее и незаметнее. Отдать модели дешевле:
голосовой ответ уже прозвучал, задержка асинхронного разбора роли не играет.

Признаки держатся **раздельно** (`mayContainMore` и `timeUnresolved`), потому что причины
разные и подсказки модели в промпте разные: «разложи фразу целиком» против «поправь время
у уже созданного события».

### Что делает модель

Разложить фразу на **все** события и создать каждое отдельным вызовом. Требования:

- **Ничего не терять.** Если часть фразы не разложилась — записать её как `note`
  со ссылкой на ту же `utterance_id`, а не проглотить.
- **Не дублировать.** Fast-path мог уже создать событие по этой же фразе — оно передаётся
  в промпте; его надо дополнить или исправить, а не создать второе такое же.
- **Порядок и время.** «Покушал и уснул» — кормление раньше сна. Если время не названо,
  ставить оба на момент фразы, но сохранять порядок в пределах секунды.
- Все события одной фразы попадают в **один `change_set`**, чтобы «отмени последнее»
  откатывало фразу целиком, а не половину.

## 10.4 Админ-дашборд `/dash`

Второй интерфейс, для мамы и папы с телефона или ноутбука — в отличие от телевизора, здесь
можно и нужно нажимать.

- **Лента истории**: время, тип, детали, источник, и **обязательно исходный текст от Алисы**
  рядом с событием — чтобы было видно, как фраза превратилась в запись, и поймать ошибки разбора.
- **Правка руками**: изменить тип, время, значение, заметку. Через тот же журнал ревизий —
  ручные правки так же обратимы, как и правки модели.
- **Удаление**: мягкое, с возможностью вернуть. Физического удаления не существует (§9.1).
- **Фильтры** по дате и типу, **аналитика**: кормлений за сутки против нормы 8–12, мокрых
  подгузников против нормы по возрасту, динамика веса и роста.
- Адаптив под телефон — смотреть будут в основном с него.

### Доступ

> **УСТАРЕЛО. Отменено §11: basic auth заменён авторизацией устройств по коду.**
> Ниже оставлено как история решения — почему API вообще понадобилось закрывать.
> Действующее описание доступа — в §11.

`/dash` закрыт HTTP Basic Auth на уровне Caddy.

**Отдельно и важно:** сейчас `/api/*` открыт всему интернету — кто угодно, зная домен, читает
всю историю ребёнка и может писать события. Basic Auth должен закрывать **и API тоже**, а не
только страницу `/dash`. Исключения ровно два:

- `/alice/<секрет>` — Алиса не умеет basic auth, её защищает секрет в пути;
- `/healthz` — нужен мониторингу и скрипту выкатки.

Телевизор при этом обязан продолжать работать: Android-приложение отдаёт учётные данные само,
через обработчик запроса аутентификации в WebView. Логин и пароль — параметры сборки, рядом
с `DASHBOARD_URL`.

# §11. Авторизация устройств по коду

Раздел §10.4 «Доступ» **устарел целиком**: basic auth на Caddy заменён авторизацией
устройств. Описание ниже отменяет его.

## 11.1 Что не так с паролем на прокси

Пароль был один на всех и **зашит в APK телевизора** параметрами сборки. Отсюда три беды:

- отозвать одно устройство нельзя — только сменить пароль сразу всем, включая телевизор,
  до которого потом надо дойти с новой сборкой;
- прокси не знает, кто пришёл, поэтому списка «кто имеет доступ» не существует в принципе;
- пароль в APK достаётся из него одной командой, и **только поэтому репозиторий обязан
  быть приватным**.

## 11.2 Поток

Device flow в духе **RFC 8628**. Мы не OAuth-сервер: ни `client_id`, ни bearer-токенов,
ни `scope`. Заимствована форма потока и, что важнее, её защитные свойства.

```
устройство                        сервер                      человек с телефоном
    │ POST /api/device/code          │                                │
    │───────────────────────────────>│                                │
    │  device_code (секрет, 256 бит) │                                │
    │  user_code   (8 символов)      │                                │
    │<───────────────────────────────│                                │
    │                                │                                │
    │  показывает user_code на экране ───────── сверяет глазами ──────>│
    │                                │  POST /api/devices/approve     │
    │                                │<───────────────────────────────│
    │ POST /api/device/token         │                                │
    │  { device_code }               │                                │
    │───────────────────────────────>│                                │
    │  Set-Cookie: bt_session=…      │                                │
    │<───────────────────────────────│                                │
```

**Два кода, а не один** — это не усложнение, а суть. `user_code` короткий, его читают с
экрана телевизора через комнату, и его энтропия — 20⁸ ≈ 34.5 бита. Если бы опрос шёл по
нему, перебор восьми символов отдавал бы **чужую** сессию. Поэтому опрос идёт только по
`device_code`: 256 бит, никогда не показывается человеку (RFC 8628 §5.1 против §5.2).

## 11.3 Короткий код

Алфавит — **base-20 из RFC 8628 §6.1**: `BCDFGHJKLMNPQRSTVWXZ`, то есть A–Z без гласных.
Гласные выброшены не только чтобы не складывались слова: вместе с ними уходят `O` и `I`,
а цифр в наборе нет вовсе. Значит пары `0/O` и `1/I` спутать **физически не на чем** —
второго участника пары в наборе не существует.

- 8 значимых символов, на экран выводится с тире: `WDJB-MJHT`;
- ввод нормализуется по §6.1: верхний регистр, пунктуация и всё вне алфавита отбрасываются,
  так что `wdjb mjht` и `WDJB-MJHT` — один и тот же код;
- **срок жизни 10 минут** (`PAIR_CODE_TTL_SEC`). Компромисс из §5.4: достаточно, чтобы дойти
  до телефона, и мало, чтобы подсмотренный или выманенный код успел пригодиться;
- код **одноразовый**: после обмена на сессию по нему больше ничего не получить.

## 11.4 Ограничители частоты

| что | предел | зачем |
|---|---|---|
| `POST /api/device/code` | 10 / 5 мин на адрес | не завалить экран одобрения мусором |
| `POST /api/device/token` | интервал 5 с, `slow_down` +5 с накопительно; потолок 120 / мин | RFC §3.5 |
| `POST /api/devices/approve` | **5 неудачных попыток / 15 мин** | RFC §5.1: ровно та цифра, при которой перебор 20⁸ бессмысленен |
| ждущих заявок одновременно | **20** | предел по самой таблице, а не по адресу |

Код неверной **длины** окна не тратит и отвечает `400 bad_code`: это опечатка, а не догадка.
Подбору поблажка не даёт ничего — код неверной длины не совпадает ни с одной заявкой в
принципе, — а человеку, у которого палец соскочил на седьмом символе, возвращает попытку.

**Одобрения по `id` заявки не существует, и это часть ограничителя, а не отдельная тема.**
Ручка `POST /api/devices/pending/:id/approve` была и удалена: `id` — это
`INTEGER PRIMARY KEY AUTOINCREMENT`, то есть маленькое последовательное число, и **никакого
счёта попыток на ней не было**. Пока она существовала, перебирать 20⁸ было незачем: хватало
перебрать `1, 2, 3`. Аккуратность соседнего эндпоинта при этом не стоила ничего.
Отклонение по `id` осталось — ошибочный отказ безвреден, устройство просто попросит заново.

Верная попытка **возвращается в окно — ровно одна**, а не сбрасывает его целиком. Разница
существенная: завести себе заявку может кто угодно (эндпоинт открыт), и полный сброс дал бы
схему «четыре неверных, одно верное своё, снова четыре», то есть предел по кругу. При этом
человек, ошибшийся при вводе и потом набравший верно, не наказан.

Ключ ограничителя для `approve` — **идентификатор сессии, а не адрес**. Адрес здесь
подделывается: у приложения включён `trustProxy` (иначе за Caddy и Cloudflare в логах был бы
адрес прокси), и он берётся из `X-Forwarded-For`, который пишет клиент.

Для открытых эндпоинтов ключом остаётся адрес — и это честная слабость: сменой заголовка окно
обходится. Терпимо, потому что заводить коды и опрашивать по 256-битному `device_code` можно
хоть миллион раз, угадать от этого нечего. От заваливания экрана одобрения защищает другое —
**предел на число ждущих заявок**, который считает по таблице и подделке адреса не поддаётся.

Счётчики живут в памяти процесса. Перезапуск их обнуляет — это осознанный размен: счётчик
попыток не данные о ребёнке, а запись в SQLite на каждый запрос ради него была бы дороже
пользы. Сам код при этом живёт десять минут и после одобрения гаснет.

Просроченные заявки помечаются `expired`, а завершённые старше семи дней удаляются: таблица
`device_codes` не история ребёнка, триггера §9 на ней нет, и расти без края ей незачем.

## 11.5 Сессии

- секрет — 32 случайных байта, в базе лежит **только `sha256`**. Утечка файла БД войти не даёт;
- кука `__Host-bt_session`: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, длинный `Max-Age`
  (без него кука сессионная и умрёт вместе с окном браузера — телевизору это не годится);
- **префикс `__Host-`** — обещание браузеру и требование к нему одновременно: такую куку
  нельзя поставить ни с соседнего поддомена, ни с другим `Path`, ни без `Secure`. Без него
  сосед по домену (что-нибудь ещё на `nuanu.ai`) мог бы подбросить `bt_session=…; Path=/dash`,
  и браузер отправил бы **её вперёд настоящей** — по RFC 6265 более длинный `Path` идёт
  первым. Это фиксация сессии, и префикс закрывает её на корню;
- сервер читает **все** куки с подходящим именем, а не первую: подброшенный мусор не должен
  заслонять настоящую сессию;
- `AUTH_COOKIE_SECURE=false` снимает `Secure` **только для локальной разработки без TLS**, и
  тогда имя обычное, `bt_session`: `__Host-` без `Secure` браузер просто выбросит. Сервер
  пишет об этом предупреждение при каждом старте.

**Сроки жизни разные, и это намеренно:**

| устройство | срок | почему |
|---|---|---|
| `tv` | **бессрочно**, только отзыв | телевизор висит на стене и показывает дневник сутками. Протухшая сессия означала бы, что однажды утром вместо журнала там код сопряжения |
| `phone`, `browser` | **скользящие 90 дней** от последнего обращения (`SESSION_TTL_DAYS`) | телефон теряют и продают, телевизор со стены — нет. Окно скользящее, а не абсолютное: телефоном, которым пользуются каждый день, не придётся переподключаться никогда, а забытый планшет сам перестанет быть ключом. Главный инструмент всё равно отзыв, срок — страховка на случай «потерял и молчу» |

**Тип устройства назначает сервер по `User-Agent`, а не клиент полем в теле.** Это не
косметика: раз у `tv` сессия бессрочная, принимать `kind` от клиента значило бы, что любой
браузер выписывает себе вечный ключ одной строкой, а девяностодневная страховка становится
делом добровольным. Клиенту остаётся выбор между телефоном и браузером — он ни на что, кроме
подписи в списке, не влияет. Подделать `User-Agent` можно, но тогда заявка и в списке
одобрения покажется телевизором, а одобрять её будет человек, который телевизор видит.

**Приставка Google TV опознаётся по слову `chromecast`.** Её `User-Agent` выглядит как
`Linux; Android 14; Chromecast Build/UTTC…; wv` — ни `android tv`, ни `crkey` в нём нет, и
до появления этого признака телевизор записывался «Телефоном Android». Цена ошибки не
косметическая: он получал скользящую девяностодневную сессию вместо бессрочной, то есть
однажды утром показал бы код сопряжения вместо дневника — ровно то, от чего эта таблица
и защищает.

**Отзыв действует немедленно и целиком.** Пометка в БД закрывает новые запросы, а уже
открытый SSE-поток сервер рвёт явно: соединение установлено, двери оно больше не
показывается, и без явного разрыва отозванный телевизор получал бы события ребёнка часами.

## 11.6 Дверь

**Одна точка проверки** — хук `onRequest` на корневом инстансе Fastify, поставленный до
регистрации чего бы то ни было. Это главное место риска всей схемы: у Fastify несколько
способов отдать ответ мимо обработчика маршрута (статика, SPA-fallback, обработчик 404),
и забыть любой из них значит открыть историю ребёнка молча — ответ будет выглядеть обычным.

**Открыт явный перечень, а не правило «всё, кроме»**: правило «всё, кроме» ошибается в
сторону открытости, перечень — в сторону закрытости.

| открыто | зачем |
|---|---|
| `/healthz` | выкатка и мониторинг |
| `/alice`, `/alice/*` | вебхук Алисы — **не трогаем вовсе**: она не умеет ни кук, ни basic auth, её защищает секрет в адресе и сверка идентичности (§3.1) |
| `/pair` | страница сопряжения |
| `/api/device/code`, `/api/device/token` | два эндпоинта потока |
| оформление PWA: `/dash/manifest.webmanifest` и иконки (`icon-192`, `icon-512`, `icon-maskable-192`, `icon-maskable-512`, `apple-touch-icon`, `favicon-32`), только `GET`/`HEAD` | браузер запрашивает их **анонимно**, без кук, и за дверью они не читались вовсе — отсюда «приложение на домашнем экране без иконки». Внутри рисунок полумесяца и название, данных нет. Перечень **поимённый**: префикс `/dash/` открыл бы всю админку |
| настоящий preflight CORS | тела не несёт, данных не отдаёт. Именно preflight — по обязательному заголовку `Access-Control-Request-Method`, а не «любой OPTIONS»: исключение по одному методу пережило бы появление первого же прикладного OPTIONS-маршрута, и тот оказался бы снаружи двери молча |

**Почему открыты файлы, а не включены куки.** Напрашивающийся `crossorigin="use-credentials"`
на `<link rel="manifest">` вернул бы куку к манифесту, но вместе с ней и требование сессии:
у того, кто уже поставил приложение на экран, а сессию потерял, иконка и имя ярлыка пропали
бы. Иконки к тому же запрашивает операционная система вне контекста страницы — при установке
ярлыка и при его обновлении, — и рассчитывать на куки там нельзя в принципе. Оформление
обязано читаться всегда, поэтому атрибута на манифесте нет.

**`/dash/sw.js` остаётся за дверью.** Иконка от воркера не зависит: ярлык ставится по
манифесту, воркер отвечает только за офлайн, а скрипт воркера по спецификации запрашивается
с credentials «same-origin», то есть с нашей же кукой.

**Ссылки на оформление в оболочке админки — абсолютные** (`/dash/manifest.webmanifest`,
не `manifest.webmanifest`). Это вторая, независимая причина той же жалобы: сервер отдаёт
оболочку и по `/dash` без слэша, а относительный `href` браузер резолвит там в корень — к
дашборду телевизора, где SPA-fallback отдаёт свой `index.html` со статусом 200 и типом
`text/html`. Манифест с чужим типом браузер игнорирует **молча**, без ошибки в консоли.

После `/alice/` разрешён **ровно один сегмент**. Префиксное правило было шире адреса, который
оно должно открывать, и эта разница стоила настоящей утечки, найденной на разборе:

```
GET /alice/../index.html      → отдавал собранный дашборд БЕЗ сессии
GET /alice/%2e%2e/index.html  → то же самое
GET /alice/..%2findex.html    → и это тоже
```

Механизм: дверь сверяла сырой путь и видела открытый префикс, а маршрутизатор и раздача
статики работали с **декодированным и нормализованным** путём, в котором `..` уже схлопнулся.
Поэтому теперь путь, содержащий `..` либо процентное кодирование точки или слеша, открытым не
считается никогда и ни при каких условиях — проверка стоит первой, до всех остальных правил.

Закрыто всё остальное **без исключений**: статика дашборда и её ассеты, `/dash` и ассеты
админки вместе с `sw.js` и манифестом, `/api/*`, SSE `/api/stream`, SPA-fallback и любые
несуществующие пути.

Сверка идёт по **сырому пути**, без декодирования процентов. Это не лень: маршрутизатор
Fastify тоже получает сырой путь, и если декодировать в двери, а там нет, то `/%68ealthz`
открылся бы как `/healthz`, а отдался бы SPA-fallback'ом, то есть дашбордом.

**Форма отказа зависит от того, кто спрашивает:**

- переход по адресу (`Sec-Fetch-Mode: navigate` или `Accept: text/html`) → `303` на
  `/pair?next=…`. Именно поэтому телевизор показывает код сопряжения, а не пустой экран;
- всё остальное → `401` с `{"error":"unauthorized","pair":"/pair"}`. Редирект в ответ на
  запрос за JSON превратился бы в «неожиданный HTML вместо данных».

Оба ответа идут с `Cache-Control: no-store`.

Значение `next` — закрытый список (`/dash` или `/`): принимать сюда что угодно значит
сделать открытый редирект, а `//evil.example` выглядит путём, но читается как чужой хост.

## 11.7 Страница сопряжения `/pair`

Один самодостаточный HTML без единого внешнего ресурса — следствие правила «открыто только
перечисленное». Будь она обычным SPA, пришлось бы открыть её бандл, шрифты и иконки, то есть
целый каталог, растущий при каждой пересборке. Одна строка HTML открывает ровно один путь.

Страница заводит заявку, показывает код крупно (читаемо и с трёх метров, и с тридцати
сантиметров), опрашивает сервер и уходит на `next` после одобрения.

**Осознанное отступление от RFC.** Спецификация советует не начинать новую заявку после
`expired_token`, пока человек не нажмёт кнопку. Здесь код обновляется сам: телевизор висит
на стене, нажать на нём некому, и «дождаться человека» означало бы вечный экран с кодом,
который уже не сработает. Обновление раз в десять минут укладывается в ограничитель с запасом.

### Почему опрос устроен странно

На боевой приставке (`Chromecast Build/UTTC…; wv`) страница завела код, человек одобрил его
за 39 секунд — и телевизор за сессией не пришёл. В базе у заявки осталось
`last_polled_at = NULL`: опроса не было **ни одного**, хотя обратный отсчёт на экране честно
дотикал все десять минут до «0:01». То есть `setInterval(…, 1000)` отработал на этом
устройстве шестьсот раз подряд, а `setTimeout(poll, 5000)` не привёл к отправке запроса ни
разу. Причина осталась неустановленной; лечение выбрано соответствующее — **не полагаться ни
на один механизм в одиночку**.

| свойство | зачем |
|---|---|
| **ни одного `setTimeout` в пути к сессии** | ровно эта конструкция и подвела: не случился один отложенный вызов — не случится больше ничего и никогда |
| **решения по часам, а не по числу тиков** | «код жив» означает `Date.now() < expires_at`, а не «таймер ещё не сработал». Таймер мог не сработать ни разу |
| **пульс из нескольких независимых источников** | `setInterval`, кадры отрисовки (`requestAnimationFrame`), событие CSS-анимации `animationiteration` и события возврата (`visibilitychange`, `pageshow`, `focus`, `online`, `resume`). Достаточно любого одного |
| **первый опрос — сразу** | из ответа на запрос кода, той же цепочкой промисов, которая на приставке доказанно работает. Заодно это единственный способ увидеть в базе, доходит ли опрос вообще |
| **срок ожидания ответа** | зависший запрос списывается через 20 с: без этого одна повисшая попытка останавливала бы сопряжение навсегда |
| **запасной транспорт** | два сбоя подряд — и опрос продолжается через `XMLHttpRequest` вместо `fetch` |

**Перезагрузка страницы заменяет опрос.** На телевизоре перезагрузка доходила до сервера
всегда, а опрос — ни разу; на пульте её вызывают MENU, кнопка Y и долгое «Назад» (оболочка,
`hardReload()`). Поэтому `device_code`, показанный код и его срок **переживают перезагрузку**:
при старте страница показывает **тот же** код и первым делом спрашивает, не одобрен ли он.
Новый код берётся только если сохранённого нет или он истёк — иначе каждое нажатие меняло бы
код на экране, и человек, набравший прежний, промахивался бы снова и снова.

Хранилище выбирается проверкой, а не верой: `localStorage`, а если запись не читается
обратно — кука с `Path=/pair` (к API не ходит). Что получилось — видно на экране. Секрет
хранится не дольше срока жизни кода и стирается сразу после обмена на сессию, отказа и
истечения.

**Экран обязан быть правдивым.** Отсчёт, состояние и диагностика — **три разных элемента**.
Пока отсчёт и состояние делили один, `tick()` раз в секунду затирал сообщение об ошибке:
«Нет связи с сервером» жило меньше секунды, то есть ошибка была, а на экране её не было.
Истёкший код гасится и подписывается «Срок кода истёк» — раньше отсчёт замирал на «0:01»,
и мёртвый код выглядел живым. Внизу постоянная строка: сколько было опросов, сколько
ответов, сколько сбоев, каким транспортом, какая память и чем кончилась последняя попытка.
У телевизора нет ни консоли, ни adb — это единственный способ узнать, что с ним происходит;
туда же выводятся необработанные ошибки JS.

## 11.8 API

**Открытые:**

- `POST /api/device/code` → `{ device_code, user_code, user_code_display, verification_uri,
  expires_in, interval }`
- `POST /api/device/token` `{ device_code }` → `200 { ok, redirect, session }` + `Set-Cookie`,
  либо `400 { error, interval }` с кодом из RFC §3.5: `authorization_pending`, `slow_down`,
  `access_denied`, `expired_token`.
  Несуществующий и протухший код отвечают **одинаково** — различать их полезно только тому,
  кто подбирает.

**За дверью:**

- `GET  /api/devices` → `{ pending[], sessions[], codeTtlSec }`.
  В `pending` **нет `userCode`** — см. §11.9
- `POST /api/devices/approve` `{ user_code }` — **единственный** способ одобрить.
  Ответы: `200 { ok, approved }`, `400 bad_code` (не та длина — окно не тратится),
  `404 not_found`, `429` с `Retry-After`.
  Несуществующий, чужой, уже разобранный и протухший код отвечают **одинаково**:
  «истёк» означало бы «такой код был», то есть подтверждение попадания
- `POST /api/devices/pending/:id/deny` — отказ по id (одобрения по id нет, см. §11.4)
- `POST /api/devices/:id/revoke`
- `GET  /api/auth/session`, `POST /api/auth/logout`

## 11.9 Экран одобрения — набрать код, а не нажать кнопку

Живёт на `#/devices`, попасть можно только из настроек. **Сам никуда не всплывает.**

Заказчик сказал дословно: «сделай страничку апрува/управления сессией по отдельному /пути
чтобы на главной не всплывало и жена случайно не одобрила никому». Дневником пользуются
двое, и второй человек только осваивает приложение.

Было три места, где заявка попадалась на глаза сама: баннер «N устройств просят доступ»
поверх любого экрана, значок «ждут: N» в настройках и список заявок с кнопкой «Одобрить»
у каждой. Убраны все три — но спрятать кнопку мало, **спрятанная кнопка остаётся кнопкой**.
Поэтому изменилось само действие.

**Одобрение требует набрать код с экрана устройства.** Так устроен и сам RFC 8628 §3.3:
сервер «prompts the end user to identify the device authorization session by entering the
`user_code`», и только потом спрашивает, одобрить или отклонить. Списка ждущих в модели
спецификации нет вовсе; наш прежний экран был формой §3.3.1 — той, где код набирать не
надо, — но без её обязательной проверки «убедитесь, что код совпадает с показанным на
устройстве».

Случайно набрать восемь букв нельзя. Попутно закрывается и неприятный случай: чужая заявка
приходит ровно в ту минуту, когда человек одобряет свой телевизор, и в списке оказываются
две — набранный код относится к одному устройству и ни к какому другому.

**Код ждущей заявки не показывается нигде и не отдаётся ни в одном ответе API.** Это не
экономия полей, а само защитное свойство: смысл набора в том, что одобряющий ОБЯЗАН БЫЛ
ВИДЕТЬ экран устройства. Код, показанный в списке, разрушает его целиком — его списывают
оттуда и впускают чужого вслепую, и «наберите код» снова становится кнопкой «Одобрить»,
только в три движения.

Список ждущих при этом остался, но отвечает ровно на один вопрос — «заявка дошла?»:
тип устройства, время запроса, сколько коду осталось жить. Плюс «Отклонить»: **ошибочный
отказ безвреден**, устройство просто попросит заново. Опасно ровно обратное действие.
Отзыв подключённого устройства тоже остался простым, в одно нажатие с подтверждением, —
по той же причине.

Опознания устройства по отпечаткам, геолокации и прочей криминалистике **нет и не будет**:
«проблемы отличать нет. я просто знаю что сейчас кто-то запрашивает одобрение, потому что
я всех знаю по именам, так как это семья». В ответе нет ни хешей, ни `user-agent`: тому,
кто знает всех по именам, они не нужны, а утечь могут.

**Опрос заявок идёт только пока экран открыт.** Фоновый опрос раз в 20 секунд существовал
ради баннера и вместе с ним потерял смысл. Сценарий «стою перед телевизором и жду» не
сломан: одобрение теперь требует взять телефон и открыть этот экран, а на открытом экране
опрос идёт раз в 5 секунд — вдвое чаще прежнего фонового.

## 11.10 Первое устройство

Замкнутый круг: одобрять надо из админки, а админка сама за дверью.

Развязывает его **команда на сервере**, а не лазейка в HTTP. Разница принципиальная:
лазейка остаётся открытой всегда и для всех, кто нашёл её адрес, а команда требует ssh —
и тот, у кого есть ssh, и так может открыть файл БД. Новых прав команда не даёт.

```bash
pnpm --filter @babytracker/server auth pending          # кто ждёт
pnpm --filter @babytracker/server auth approve XXXX-XXXX
pnpm --filter @babytracker/server auth list             # кто подключён
pnpm --filter @babytracker/server auth revoke <id>      # отозвать
pnpm --filter @babytracker/server auth issue --kind tv  # выпустить сессию напрямую
```

Подробности — в [DEPLOY.md](DEPLOY.md).

## 11.11 Схема БД

Миграция (`user_version` 4 → 5) строго **аддитивная**: две новые таблицы, ни одного `ALTER`
и ни одного `DROP`. Откат к предыдущему коду их просто не замечает.

```sql
CREATE TABLE IF NOT EXISTS device_sessions (
  id            TEXT PRIMARY KEY,       -- публичный id для списка и отзыва
  token_hash    TEXT NOT NULL UNIQUE,   -- sha256 секрета из куки
  kind          TEXT NOT NULL,          -- 'tv' | 'phone' | 'browser'
  label         TEXT,
  user_agent    TEXT,
  created_at    TEXT NOT NULL,
  last_seen_at  TEXT NOT NULL,
  expires_at    TEXT,                   -- NULL = бессрочно (телевизор)
  revoked_at    TEXT
);

CREATE TABLE IF NOT EXISTS device_codes (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  device_code_hash  TEXT NOT NULL UNIQUE,
  user_code         TEXT NOT NULL,
  kind              TEXT NOT NULL,
  label             TEXT,
  user_agent        TEXT,
  status            TEXT NOT NULL,      -- pending|approved|claimed|denied|expired
  created_at        TEXT NOT NULL,
  expires_at        TEXT NOT NULL,
  approved_at       TEXT,
  approved_by       TEXT,
  claimed_at        TEXT,
  session_id        TEXT,
  last_polled_at    TEXT,
  interval_sec      INTEGER NOT NULL DEFAULT 5
);

-- Два ждущих устройства с одинаковым коротким кодом означали бы, что одобрение
-- уходит не тому. Частичный индекс делает это невозможным, не мешая истории.
CREATE UNIQUE INDEX IF NOT EXISTS idx_device_codes_pending
  ON device_codes(user_code) WHERE status = 'pending';
```

`user_code` хранится открытым текстом **осознанно**: его показывают одобряющему, чтобы он
сверил код с экраном устройства. Хеш сделал бы экран одобрения невозможным, а защищает этот
код не тайна хранения, а десять минут жизни и ограничитель попыток.

## 11.12 Клиенты

**Телевизор** (`apps/tv`). Экран сопряжения — обычная веб-страница, Kotlin не рисует ничего.
От него требуется другое: **хранить куку**. `CookieManager` включается явно (умолчание
зависит от прошивки и версии System WebView), и куки сбрасываются на диск `flush()` при
паузе и после каждой успешной загрузки — телевизор чаще выключают из розетки, чем закрывают
приложение, и `onPause` может не случиться вовсе. Пароль в сборке больше не нужен;
параметры `DASHBOARD_USER` / `DASHBOARD_PASSWORD` оставлены до снятия basic auth на боевом
сервере, чтобы APK из этой ветки работал и со старым сервером.

**Админка** (`apps/admin`). Экран «Устройства» (`#/devices`, только из настроек): поле для
ввода кода с экрана устройства, список ждущих **без кодов** с одним «Отклонить», список
подключённых с отзывом, выход. На главный экран не всплывает ничего — ни баннера, ни
счётчика заявок (§11.9).

Поле ввода показывает код так же, как он написан на устройстве (`WDJB-MJHT`), а хранит без
тире. Каретку приходится держать в конце руками: показанная строка на пятом символе
становится на знак длиннее набранной, React возвращает каретку на прежнее смещение — и она
оказывается ПЕРЕД только что введённой буквой, после чего код тихо собирается неверным.
Поймано вживую: тык в середину поля и три буквы превратили `GXWKZ` в `ZFLG-XWKZ`.
Выглядит это как «сервер не принимает верный код», а стоит одной из пяти попыток за окно.

*Про PWA.* Service worker держит в кэше и оболочку, и последние ответы API. Две тихие
ловушки:

1. без сессии сервер отвечает на переход **редиректом**, `fetch` следует за ним молча и
   возвращает вполне успешный `200` — страницу сопряжения. Положив её в кэш под именем
   оболочки, воркер намертво подменил бы дневник экраном сопряжения, и это пережило бы даже
   возврат сессии. Поэтому ответы с `redirected === true` в кэш не попадают никогда;
2. после потери доступа тот же кэш означал бы, что человек, взявший потерянный телефон,
   включает авиарежим, открывает приложение и читает историю ребёнка, ни разу не дойдя до
   сервера, — то есть отзыв, ради которого всё затевалось, оказался бы бесполезен. Поэтому
   кэш сносится **при первом же признаке потери доступа**: и при явном выходе, и на `401`,
   и на редирект к сопряжению. Не кэшировать `401` недостаточно — опасен уже сохранённый.

Файл `sw.js` закрыт дверью, как и всё под `/dash`. Это работает потому, что скрипт воркера
запрашивается в режиме credentials `same-origin`, а регистрация идёт из уже загруженного
приложения, у которого сессия есть. Полезный побочный эффект: после выхода воркер не сможет
ни обновиться, ни установиться заново. Если какой-то браузер куку всё же не пришлёт, отказ
мягкий: приложение останется рабочим, просто без офлайна, и напишет об этом в консоль.

**Дашборд** (`apps/dashboard`). При `401` уходит на `/pair`: на телевизоре нет ни консоли,
ни клавиатуры, и разбираться, почему дневник пропал, там некому.
