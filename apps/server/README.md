# @babytracker/server

Бэкенд BabyTracker: вебхук Яндекс Диалогов, REST + SSE для дашборда, фоновый разбор фраз
через `claude -p`, отдельный MCP-сервер и раздача собранного дашборда статикой.

Контракт, которому всё здесь подчиняется: [`../../docs/CONTRACT.md`](../../docs/CONTRACT.md).

## Требования

- **Node >= 24.** Используется встроенный `node:sqlite` (`DatabaseSync`), а не `better-sqlite3`:
  на проде нет C++ тулчейна и мало диска, нативный модуль там не соберётся.
- pnpm 10.
- TypeScript исполняется Node напрямую (type stripping) — шага сборки нет,
  `pnpm typecheck` только проверяет типы.

## Запуск

```bash
cd apps/server
pnpm install

# минимум для локального старта
export ALICE_WEBHOOK_SECRET=$(openssl rand -hex 16)
pnpm dev          # с автоперезапуском
# или
pnpm start
```

Сервер слушает `0.0.0.0:8787`. Файл `.env` рядом с `package.json` подхватывается автоматически
(`--env-file-if-exists`); за образец возьмите `../../.env.example`.

| `ALICE_IDENTITY_CHECK` | `true` | `false` — не сверять идентичность вовсе, только фиксировать обращения |

| `WORKER_ENABLED` | `true` | Выключает фоновый разбор |
| `LLM_QUEUE_POLICY` | `smart` | Когда звать модель: `smart` / `all` / `unknown` (§9.4) |
| `LLM_CONFIDENCE_THRESHOLD` | `0.8` | Ниже этой уверенности fast-path зовём модель |

запроса до `/alice/***`, а дочерним процессам (`claude`, MCP-сервер) переменная не передаётся.

`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`
**вычищаются из окружения дочернего `claude`**: с ними CLI молча уходит на поштучную оплату
по API мимо подписки. Если такая переменная есть в окружении — при старте будет предупреждение.

## Раздача статики

Сервер отдаёт оба интерфейса сам, чтобы на Android TV не требовался второй веб-сервер
и не было кросс-origin:

| Путь | Что отдаётся | Откуда |
|---|---|---|
| `/` | дашборд телевизора | `DASHBOARD_DIST` |
| `/dash`, `/dash/`, `/dash/assets/*` | админка | `ADMIN_DIST` |

- **Телевизор** — обычная SPA: неизвестный `GET` вне `/api`, `/alice`, `/healthz` и `/dash`
  отдаёт её `index.html` (SPA-fallback).
- **Админка** собрана с `base: '/dash/'` и использует хэш-роутинг (`/dash/#/history`),
  поэтому SPA-fallback ей не нужен: сервер отдаёт `index.html` на `/dash` и `/dash/`,
  ассеты по `/dash/assets/*`, а неизвестный `/dash/что-то` — честный `404` JSON.
  Дашборд телевизора под `/dash` не показывается никогда.

### Админка это PWA: заголовки — часть работоспособности

Оба отказа ниже происходят **молча**, без единой ошибки в консоли, и потому
отлаживаются мучительно. Поэтому они зафиксированы тестами.

| Файл | Content-Type | Cache-Control |
|---|---|---|
| `/dash/manifest.webmanifest` | `application/manifest+json` | `no-cache` |
| `/dash/sw.js`, `/dash/service-worker.js` | `application/javascript` | `no-cache` |
| `/dash`, `/dash/` (оболочка) | `text/html` | `no-cache` |
| `/dash/assets/*` (имя с хешем) | по расширению | `max-age=31536000, immutable` |
| прочее верхнего уровня (иконки, `registerSW.js`) | по расширению | `no-cache` |

- Манифест с чужим типом браузер **игнорирует**, и установка на домашний экран
  просто не предлагается. Тип задаётся хуком `onSend`, а не `setHeaders`:
  `send` выставляет Content-Type **после** `setHeaders` и затирает его —
  проверено фактом.
- Service worker с длинным кешированием застревает вместе со всей старой версией
  приложения. `no-cache` — это не «не кешировать», а «каждый раз переспросить».
- Что кешировать навсегда, определяется **расположением, а не списком имён**:
  Vite кладёт в `assets/` файлы с хешем содержимого. Остальное имя не меняет.
- Область воркера: `Service-Worker-Allowed: /dash/` — ровно его собственный путь.
  Шире не выдаём: дашборду телевизора на `/` воркер админки управлять не должен.
- **Файлов PWA может ещё не быть** — тогда на них честный `404`, всё остальное
  работает как обычно.
- `/api/*` всегда возвращает честный `404 {"error":"not_found"}`, а не `index.html`.
- **Каталога `dist` нет — это не ошибка, ни для одного из двух.** Сервер пишет одну
  строку в лог и продолжает работать: в dev-режиме интерфейсы крутятся на Vite отдельно.
  Для этого случая и нужен `DASHBOARD_ORIGIN`.

## Проверка курлом

```bash
SECRET=<ваш ALICE_WEBHOOK_SECRET>
B=http://127.0.0.1:8787

# 1. приветствие (новая сессия, пустая команда)
curl -s -X POST "$B/alice/$SECRET" -H 'Content-Type: application/json' -d '{
  "session":{"session_id":"s1","skill_id":"k","user_id":"u1","new":true},
  "request":{"type":"SimpleUtterance","command":"","nlu":{}},"version":"1.0"}'

# 2. заснул  (замеряем и время ответа: бюджет 200 мс)
curl -s -w '\nвремя: %{time_total}s\n' -X POST "$B/alice/$SECRET" -H 'Content-Type: application/json' -d '{
  "session":{"session_id":"s1","skill_id":"k","user_id":"u1"},
  "request":{"type":"SimpleUtterance","command":"андрей заснул","nlu":{}},"version":"1.0"}'

# 3. проснулся
curl -s -X POST "$B/alice/$SECRET" -H 'Content-Type: application/json' -d '{
  "session":{"session_id":"s1","skill_id":"k","user_id":"u1"},
  "request":{"type":"SimpleUtterance","command":"андрей проснулся","nlu":{}},"version":"1.0"}'

# 4. сводка
curl -s -X POST "$B/alice/$SECRET" -H 'Content-Type: application/json' -d '{
  "session":{"session_id":"s1","skill_id":"k","user_id":"u1"},
  "request":{"type":"SimpleUtterance","command":"сколько он сегодня спал","nlu":{}},"version":"1.0"}'

# 5. неверный секрет -> 200 OK с нейтральным текстом, ничего не записывается
curl -s -X POST "$B/alice/ffffffffffffffffffffffffffffffff" -H 'Content-Type: application/json' \
  -d '{"session":{"user_id":"x"},"request":{"command":"андрей заснул"},"version":"1.0"}'

# REST
curl -s "$B/api/state"
curl -s "$B/api/events?limit=5"
curl -s "$B/api/sleep/daily?days=14"
curl -s "$B/api/utterances?limit=10"
curl -s "$B/healthz"

# ручная запись события (отладка)
curl -s -X POST "$B/api/events" -H 'Content-Type: application/json' \
  -d '{"type":"feed","subtype":"bottle","value_num":120,"value_unit":"ml"}'

# SSE: держите открытым в соседнем терминале и шлите события из первого
curl -sN "$B/api/stream"
```

В потоке SSE должны быть: `retry:`, `event: state` сразу после подключения, затем
`event: event` / `event: utterance` на каждое действие и комментарий-heartbeat `: ping`
раз в 15 секунд.

## Кто такой владелец: аккаунт, а не устройство

Прод-инцидент: белый список читал `session.user_id` и **трижды заблокировал заказчика** —
после тестирования в консоли, после повторной попытки и после публикации навыка.

Причина в документации Яндекс Диалогов: `session.user_id` **устарело** и идентифицирует
*экземпляр приложения*. «Даже если пользователь вошёл в один и тот же аккаунт в приложение
Яндекс для Android и iOS, Яндекс Диалоги присвоят отдельный `user_id` каждому из этих
приложений». Консоль, телефон и каждая колонка в доме дают разные значения.

| поле | что это | когда приходит |
|---|---|---|
| `session.user.user_id` | **аккаунт Яндекса**, один на все устройства | только если пользователь авторизован |
| `session.application.application_id` | устройство (актуальная замена `user_id`) | всегда |
| `session.user_id` | устройство, **устаревшее поле** | всегда |

Сервер опознаёт по аккаунту, если он есть, и откатывается на устройство, если нет.
Поэтому **вторая колонка того же аккаунта работает сразу**, без ручного добавления.

### Модель доверия

- **Доверие первому.** На чистой установке первое обращение запоминается как владелец —
  в БД, а не в `.env`, так что переживает перезапуск и деплой. Срабатывает ровно один раз
  за жизнь установки: иначе снятие доверия у единственного устройства тут же возвращало бы его.
- **Вход в аккаунт не запирает.** Если аккаунт впервые виден с уже доверенного устройства,
  он тоже становится доверенным (`source=promoted`).
- **Заданный `ALICE_ALLOWED_USER_IDS` уважается** и сверяется со всеми тремя полями —
  на проде там лежат значения устаревшего `user_id`. Если он задан, доверие первому выключено.
- **Незнакомое устройство не запирается молча:** отличимый от сбоя ответ («Это устройство
  пока не подключено…»), одна строка в логе со всеми тремя полями и готовой командой,
  и запись в `GET /api/alice/pending`.

### Подключить новую колонку с телефона

```bash
# что именно к нам стучалось
curl -s "$B/api/alice/pending"
# подтвердить конкретное обращение
curl -s -X POST "$B/api/alice/pending/<id>/trust"

# либо: открыть окно и сказать что-нибудь новой колонке
curl -s -X POST "$B/api/alice/enroll" -H 'Content-Type: application/json' -d '{"minutes":10}'

# снять доверие
curl -s -X DELETE "$B/api/alice/identities/<id>"
# всё, что известно о устройствах и аккаунтах
curl -s "$B/api/alice/identities"
```

`skill_id` запоминается по первому обращению (`ALICE_SKILL_ID` в env, если задан, остаётся
жёстким рубежом). Ручки `/api/alice/*` закрыты сессией устройства (§11) вместе с остальным
`/api/*`. Сам вебхук `/alice/*` при этом открыт: Алиса не умеет ни кук, ни basic auth.

### Насколько это вообще нужно

Настоящая защита вебхука — **32-символьный секрет в пути**: 128 бит, известные только консоли
Яндекса и серверу. Сверка идентичности — второй рубеж на случай утечки секрета, и её цена уже
один раз превысила пользу: заказчика заперло трижды, а Алиса говорила «Извините, сейчас не могу
ответить», как при падении сервера. Поэтому здесь она переделана так, чтобы **отказ был
восстановим без ssh и заметен**, и добавлен `ALICE_IDENTITY_CHECK=false` — если она снова
начнёт мешать больше, чем защищать, её выключают одной переменной, а обращения продолжают
записываться и видны в админке.

## Несколько событий в одной фразе (§10.3)

Мама говорит свободно: «Андрей покушал и уснул». Fast-path видит здесь уверенный
`sleep_start` (0.95) — и без защиты политика `smart` не позвала бы модель,
а кормление исчезло бы **молча**: мама уверена, что записала, а записи нет.

Поэтому ### Принцип: белый список, а не оценка уверенности

После **трёх** одинаковых инцидентов на проде — «покушал и уснул», «заснул
полтора часа назад», «что он закончил кушать когда лег спать» — направление
решения перевёрнуто. Каждый раз список опасностей дописывали уже ПОСЛЕ того,
как он подвёл, и каждый раз ценой потерянного факта. В третьей фразе дыр было
сразу две: «когда» не входило в список связок, «кушать» не покрывалось стемами
еды. Полный список русских связок не составить.

Было: «матчер уверен → модель не зовём».
Стало: **«фраза совпала с короткой канонической формой → не зовём; всё
остальное → зовём»** (`checkCanonical` в `fastpath.ts`).

Канонична фраза, в которой **каждое слово матчеру знакомо**, и при этом она
короткая (до 4 значимых слов), без чисел, без времени, не вопрос и не составная.
Незнакомое слово — самостоятельная причина отдать фразу модели. Чтобы дыра
появилась теперь, надо ошибочно **добавить** слово в белый список, а не забыть
добавить в чёрный — тот же приём, что со списком колонок в валидаторе SQL.

Это дороже по вызовам, и осознанно: цена лишнего вызова — часть окна лимита
подписки, цена пропущенного факта — потерянная запись в дневнике ребёнка,
которой никто не хватится.

Голосовой ответ по-прежнему формирует матчер и по-прежнему мгновенно —
меняется только то, кто выносит окончательное решение о данных.

`LLM_QUEUE_POLICY`: `all` и `unknown` прежние, `smart` означает новое поведение.
Признаки `mayContainMore`, `timeUnresolved` и команды правки данных перебивают
любую политику, включая `unknown`.

### Подгузник в матчере

Однословные «покакал» / «пописал» матчер записывает сам (`type=diaper`): это
единственный не-сонный факт, где ошибиться негде. Иначе такая фраза не была бы
канонической и уходила бы модели — или, что хуже, терялась бы.

### Если факт всё-таки потерян

```bash
curl -s "$B/api/utterances?limit=20"              # найти подозрительную фразу
curl -s -X POST "$B/api/utterances/<id>/reparse"  # разобрать заново
```

Фраза возвращается в очередь независимо от политики, счётчик попыток
обнуляется, `reparse_count` растёт. Модель получает в промпте блок «это
повторный разбор» и события, уже созданные по этой фразе, — дополняет
недостающее, а не создаёт заново. В админке это кнопка у строки ленты.

### Признаки, перебивающие политику

`matchFast` возвращает ещё и `mayContainMore: boolean`. Он `true`, если:

- есть союз или перечисление: ` и `, ` а `, ` потом`, ` затем`, ` после`, `,`, ` плюс`;
- встретилось ключевое слово из другого домена (еда, подгузник, измерение, лекарство,
  симптом, активность, сцеживание);
- во фразе больше одного числа (считаются и цифры, и «пятнадцать»);
- значимых слов больше шести.

При `mayContainMore === true` фраза уходит модели **независимо от confidence и
`LLM_QUEUE_POLICY`**. Голосовой ответ при этом остаётся мгновенным и по тому, что
понял fast-path — мама не ждёт.

Все события одной фразы (включая то, что успел записать fast-path) попадают в
**один `change_set`**, поэтому «отмени последнее» откатывает фразу целиком.

### Неразрешённое время

Второй признак того же класса, найденный на проде: «андрей заснул полтора часа назад»
при пустом `nlu.entities` записывался на **текущий момент** с уверенностью 0.95 и потому
не уходил модели — правдоподобное, но неверное время без единого признака ошибки.

`matchFast` возвращает ещё и `timeUnresolved: boolean` — «время во фразе названо,
а разобрать его не удалось» (`назад`, `в три`, `утром`, `после обеда`, `полчаса`,
`только что`, `вчера`, …). При `true`:

- confidence падает до **0.4** и сохраняется в `events.confidence` — неуверенность видна
  в дашборде, а не только в логе;
- фраза уходит модели независимо от политики и порога;
- событие всё равно создаётся (при недоступной модели неточная запись лучше, чем никакой),
  но **голос не называет время**: «Записала: Андрей заснул. Время уточню»;
- модель получает в промпте указание поправить `started_at`, а не создавать второе событие.

Относительное время сервер **намеренно не разбирает сам**: русские временные выражения
слишком разнообразны, а наполовину работающий разбор даёт ту же правдоподобную неправду,
только увереннее. Отдать модели дешевле — голосовой ответ уже прозвучал.

## Неоднозначность: что делает модель, когда сведения неполные

Сведения приходят неполные, противоречивые и не по порядку — это норма работы,
а не сбой. Политика живёт в `src/prompt.ts` и держится на одной границе:

> **Решать о прочтении — можно и нужно. Выдумывать факты — нельзя никогда.**

Выбрать вероятнейшее прочтение фразы и действовать по нему — это владение
данными. Сочинить время, объём или длительность, которых никто не называл,
чтобы история вышла связной, — та самая ошибка, которую проект уже дважды
ловил на проде (относительное время, §10.3): правдоподобно, аккуратно и неверно.

### Как выглядит допущение в данных

Два поля, всегда вместе — отдельной колонки-флага нет намеренно:

| поле | что несёт | кому |
|---|---|---|
| `note`, начинающаяся с `[?]` | **что именно** неизвестно и почему выбрано это прочтение, словами | человеку в ленте `/dash` |
| `confidence` | **насколько** можно верить записи | дашборду |

`confidence`: 0.9–1.0 — всё названо прямо; 0.7–0.85 — факт назван, выведена
деталь; 0.4–0.6 — выбрано одно из прочтений; 0.2–0.35 — запись существует,
чтобы не потерять сказанное. Значение **не выше 0.6 обязательно**, если
выведенное моделью попало в `type`, `started_at`, `ended_at` или `value_num`:
именно эти поля становятся часами сна и миллилитрами на дашборде.

Маркер `[?]` — контракт, а не стиль: ASCII, стабильный, грепается
(`note LIKE '[?]%'`), одинаков у записей модели и быстрого матчера — заметку
«проснулся, а засыпание не записано» матчер тоже помечает им. В коде —
`ASSUMPTION_MARK` и `isAssumption()` из `src/prompt.ts`.

Нужно число, которого не называли, — ставится **граница**, которую можно
защитить («позже этого момента он точно не спал»), и она названа границей
в заметке. «Типичное» и «примерное» не ставится никогда.

### Канонический случай

«Андрей заснул», а через три часа снова «Андрей заснул», про пробуждение
не говорили. Прочтения три, и различить их нельзя: проснулся и забыли сказать;
родитель повторился; первое «заснул» было ошибкой. Выбор между первыми двумя
делает **прошедшее время** — повтор через 10 минут бывает, новое засыпание
через 10 минут нет:

- в пределах 20 минут — повтор фразы: открытый сон не трогается, второй
  не создаётся, пишется заметка с `[?]`;
- дольше — пропущенное пробуждение: открытый сон закрывается **моментом фразы
  как границей** (позже него ребёнок точно не спал), с `[?]` и `confidence` 0.2–0.3,
  и заводится новый сон. Любое «красивое» время пробуждения между двумя
  фразами было бы выдумкой, поэтому его не ставят.

### Длительные события: `ended_at` = «идёт», а не «конец неизвестен»

Живой случай с прода: «начал кушать» → модель завела **открытое** кормление
и не выдумала ни вид, ни объём — правильно. Но у сна есть пара
«заснул / проснулся» и инвариант одного открытого сна, а у кормления нет
ничего: запись провисит до утра и покажет «идёт седьмой час».

Политика — одна на все типы с длительностью (`sleep`, `feed`, `pump`,
`activity`; всё остальное точечное всегда):

- **вид глагола решает**: «покормила», «поел», «искупали» — законченный факт,
  `ended_at = started_at`; «начал кушать», «кормлю», «купаемся» — идёт,
  `ended_at` пустой;
- **закрывают** открытое «поел», «доел», «закончил», «всё», «пришли
  с прогулки». Момент тут **назван** — родитель говорит в ту самую минуту,
  поэтому `ended_at = сейчас`, `confidence` высокая, маркер не нужен;
- **провисевшее** (кормление или сцеживание старше часа, активность старше
  трёх) закрывается **точкой**: `ended_at = started_at` и `[?]` «не закрывали,
  длительность неизвестна». `value_num` при этом не трогается — неизвестная
  длительность это NULL, а не число;
- **почему точкой, а у сна границей**: `ended_at` сна — это часы на дашборде,
  и точка стёрла бы реальный сон. У кормления, сцеживания и активности
  длительность в метрики не идёт (`dailyStats` считает кормления штуками,
  а объём берёт из `value_num`), поэтому точка ничего не теряет, а граница
  нарисовала бы шестичасовое кормление, которого не было;
- **новое такое же при открытом предыдущем** — та же развилка, что со вторым
  «заснул»: в окне повтора это повтор фразы, дальше — предыдущее просто
  не закрыли.

Пороги — `MAX_OPEN_MIN` и `isStaleOpen()` в `src/prompt.ts`.

**Чего эта политика не закрывает.** Подчистка выполняется, только когда
модель вообще позвана, а при `LLM_QUEUE_POLICY=smart` уверенное «заснул»
её не зовёт: открытое кормление может провисеть до следующей непонятой фразы.
Надёжно это чинится на уровне кода — периодический проход по
`type IN ('feed','pump','activity') AND ended_at IS NULL`, старше `MAX_OPEN_MIN`,
закрывающий их точкой через журнал (`actor='api'`). Это правка в `events.ts`
или в воркере, не в промпте; здесь она намеренно не сделана — файл сейчас
за другим владельцем.

### Структура промпта

Промпт — интерфейс, а не сочинение, поэтому он собирается из трёх слоёв:

1. **всегда** — главное правило, механика пометки, порядок работы и таблица
   однострочных вердиктов по всем разобранным случаям;
2. **по ситуации** — до трёх развёрнутых разборов ровно тех случаев, которые
   сейчас на столе (открытый сон при новом «заснул», поправка, противоречие,
   дословный повтор, пробуждение без сна, запись задним числом, свежий дубль),
   с готовыми образцами вызовов и посчитанными числами;
3. **всегда** — справочники: таксономия, тулы, схема, рамки SQL.

Семь подробных разборов подряд превращаются в фон, из которого модель
выхватывает случайный, поэтому лимит — `MAX_CASE_CARDS`. Базовый промпт
держится около 9 тысяч символов, худший случай — около 12 тысяч; тест
`test/ambiguity.test.ts` следит за этим, потому что избыточный промпт
ухудшает следование инструкциям не меньше, чем недостаточный.

### Голосовой ответ

Матчер отвечает **до** модели, поэтому озвучить он может только ту
неопределённость, которую видит сам, — и три такие уже озвучивает:
«Андрей уже спит, с 17:32» (открытый сон), «А он и не спал» (пробуждение
без сна), «Время уточню» (неразобранное время). Всё, что находит модель,
приходит после того, как Алиса замолчала, и доходит до родителя двумя путями:
лента `/dash` по SSE (там видны `[?]` и `confidence`) и итоговая строка
набора изменений. Толкнуть реплику в закрытую сессию Алиса не умеет.

## Таксономия событий (§10.2)

`sleep`, `feed` (breast/bottle/solid), `pump`, `diaper` (wet/dirty/both),
`measure` (weight/height/**head**/temp), `meds`, `symptom`, `activity`, `note`.
Один источник правды — `src/taxonomy.ts`; оттуда же берутся enum'ы валидации API,
схемы MCP-тулов и справочник в промпте.

**Объём необязателен везде.** При смешанном вскармливании граммы осмысленны только
для бутылочки, грудь измеряют стороной и длительностью. Не названное мамой число —
это `NULL`, а не ноль: ноль означал бы «покормили нулём миллилитров». В промпте
это сказано модели прямым текстом, а `/api/stats/daily` отдаёт `volumeMl: null`,
если объём не называли ни разу.

Неизвестный `subtype` — не повод терять событие: пишется `type` с `note`.

## Обратимость изменений (§9)

Модель получает широкий доступ к SQL, поэтому безопасность даёт не доверие к ней,
а конструкция хранилища. **Безвозвратной модификации данных не существует.**

Три независимых рубежа:

1. **Триггер SQLite `events_no_hard_delete`.** Физически удалить событие нельзя ничем —
   ни тулом, ни произвольным SQL, ни багом в коде, ни через `sqlite3` из консоли.
   Удаление выражается только через `deleted_at`. Журнал ревизий тоже защищён
   от UPDATE и DELETE: он строго append-only.
2. **Журнал ревизий.** Каждое изменение `events` пишет полный снимок строки «до»
   в `event_revisions`, изменения одного запуска модели объединены в `change_set`.
   Любую правку можно отменить хоть через месяц — в том числе отмену отмены.
3. **Снимок базы** (`VACUUM INTO data/snapshots/<время>.db`) перед каждым запуском
   модели, хранятся последние 50.

Проверить рубеж 1 руками:

```bash
sqlite3 data/babytracker.db "DELETE FROM events;"
# Error: stepping, физическое удаление events запрещено: используй deleted_at (19)
```

Отмена изменений:

```bash
curl -s "$B/api/change-sets?limit=5"
curl -s -X POST "$B/api/change-sets/<id>/revert"
curl -s "$B/api/events?include_deleted=true"   # посмотреть, что было скрыто
```

### Рамки произвольного SQL

`sql_execute` принимает **один** `INSERT INTO events` или `UPDATE events`. Отклоняются
`DELETE`, любая другая таблица, DDL и служебные команды, вторая команда за `;`,
изменение `id` / `created_at` / `utterance_id`. Проверка идёт по токенам, а не по
подстрокам: `note = 'не надо delete'` — валидный запрос, а `-- ;\nDROP TABLE` — нет.
Текст ошибки всегда содержит подсказку, что сделать вместо.

`sql_query` выполняет произвольный `SELECT` по любым таблицам, до 500 строк.

### Лимиты подписки

Вызовы идут через подписку, поэтому ограничитель — окна лимитов, а не деньги.
Воркер отличает «лимит исчерпан» от настоящей ошибки: фраза возвращается в очередь
**без расхода попытки**, воркер встаёт на паузу до времени сброса окна (или на
экспоненциальную паузу от минуты до часа, если время не названо). В `/healthz` это
отдельное состояние `worker.rateLimited` / `rateLimitedUntil` — не путать с
`claudeAvailable: false`, которое означает сломанный или неавторизованный CLI.

## Админ-API для дашборда `/dash` (§10.4)

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/events?from&to&type&limit&include_deleted` | лента истории; **у каждого события есть `utterance_text`** — исходная фраза Алисы (LEFT JOIN по `utterance_id`) |
| `PATCH` | `/api/events/:id` | правка типа, времени, значения, заметки. Через журнал, `actor='manual'`; в ответе `changeSetId` для отката |
| `DELETE` | `/api/events/:id` | мягкое удаление через журнал; в ответе `revertWith` |
| `GET` | `/api/stats/daily?days=N` | кормления, мокрые/грязные подгузники, сон, вес/рост/окружность головы и **нормы для текущего возраста** |

Ручные правки так же обратимы, как правки модели: `POST /api/change-sets/:id/revert`.

Нормы (§10.1, ориентиры AAP) считаются от `CHILD_BIRTHDATE`: мокрые подгузники
день 1 → 1, день 2 → 2, … с 5-го дня 6+; кормления 8–12 в сутки; грязные 3–4.
Каждая норма отдаётся с пояснением текстом, чтобы дашборд не выдавал ориентир
за жёсткий порог.

## Аутентификация: устройства по коду (§11)

Раньше сторожил Caddy, и сторожил всё скопом. Теперь проверка — **дело приложения**,
и живёт она в одном месте: `src/auth-guard.ts`, хук `onRequest` на корневом инстансе,
поставленный **до регистрации чего бы то ни было**.

Порядок регистрации здесь не стилистика. У Fastify несколько способов отдать ответ мимо
обработчика маршрута — статика, SPA-fallback, обработчик 404 — и забыть любой из них
значит открыть историю ребёнка молча: ответ будет выглядеть совершенно обычным. Что хук
видит их все, проверено опытом (`test/device-auth-guard.test.ts`), а не предположением.

Открыт **явный перечень**, а не правило «всё, кроме»: правило «всё, кроме» ошибается
в сторону открытости.

| открыто | зачем |
|---|---|
| `/healthz` | мониторинг и скрипт выкатки |
| `/alice`, `/alice/*` | вебхук: Алиса не умеет ни кук, ни basic auth |
| `/pair` | страница сопряжения (один самодостаточный HTML, `src/pair-page.ts`) |
| `/api/device/code`, `/api/device/token` | два эндпоинта потока |

Закрыто всё остальное: статика дашборда и её ассеты, `/dash` вместе с `sw.js` и манифестом,
`/api/*`, SSE, SPA-fallback, несуществующие пути.

Сверка идёт по **сырому пути**, без декодирования процентов: декодировать здесь и не
декодировать в роутере значило бы открыть `/%68ealthz` как `/healthz`, а отдать по нему
SPA-fallback, то есть дашборд.

Форма отказа зависит от того, кто спрашивает: переход в браузере получает `303` на
`/pair?next=…`, всё остальное — честный `401`. Редирект в ответ на `fetch` за JSON
превратился бы в «неожиданный HTML вместо данных».

**SSE здесь удобнее, а не сложнее.** `EventSource` не умеет слать `Authorization` — это и
было главным неудобством basic auth. Кука уходит сама, без единой строчки на клиенте.
Взамен появляется обязанность: отзыв устройства должен рвать **уже открытый** поток
(`SseHub.closeSession`), иначе отозванный телевизор получал бы события ребёнка часами —
двери он больше не показывается.

Заголовки `Authorization` и `Cookie` вырезаются из логов (`redact`).

Первое устройство одобряется командой на сервере — `src/auth-cli.ts`, см. docs/DEPLOY.md.
Лазейки в HTTP для этого нет намеренно.

## Работа без claude

LLM — усилитель, а не единая точка отказа. Если `claude` не установлен или не авторизован:

- при старте в лог уходит **ровно одна** строка `worker: claude CLI недоступен`;
- фразы из очереди помечаются `skipped`, попытки не жгутся;
- fast-path продолжает писать события, Алиса отвечает как обычно;
- `/healthz` показывает `worker.claudeAvailable: false` и причину;
- раз в 5 минут воркер молча пробует, не ожил ли CLI, и подхватывает его без рестарта.

Проверить:

```bash
CLAUDE_BIN=/nonexistent pnpm start
```

## MCP-сервер

Отдельный stdio-процесс поверх того же файла БД. Воркер сам пишет `mcp.json` рядом с БД
и передаёт его в `claude --mcp-config`. Запустить вручную:

```bash
DB_PATH=./data/babytracker.db pnpm mcp
```

Тулы:

- простые: `get_state`, `query_events`, `log_event`, `update_event`, `delete_event`, `sleep_daily`;
- широкие (§9.3): `sql_query`, `sql_execute`;
- отмена: `list_change_sets`, `revert_change_set`.

Ничего, кроме них, модели не дано: ни bash, ни записи файлов.
